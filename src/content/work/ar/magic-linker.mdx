## 01 · السياق والمشكلة

منصة ماجيك لينكر تجمع الموردين والمتاجر والموزعين في اليمن لتقديم تجربة شراء جملة (B2B) وتجزئة (B2C) في مكان واحد. المشتري يضيف منتجات من عدة تجار في سلة واحدة ويتوقع دفعاً واحداً بعملته المفضلة، بينما يحتاج كل تاجر لوحة مستقلة لطلباته ومخزونه ومستحقاته الصافية بعد خصم عمولة المنصة دون أي تداخل مع بيانات التجار الآخرين.

## 02 · القيود الهندسية

- **تعدد بوابات الدفع والعملات:** لا توجد بوابة واحدة تغطي كل البطاقات الإقليمية والدولية، ما فرض دمج **Stripe** و**PayPal** و**Moyasar** معاً بواجهة برمجية موحدة.
- **تذبذب شبكات الموبايل:** إعادة الضغط على زر الدفع وتكرار وصول الـ Webhooks حالات طبيعية يومية ويجب ألا تسبب خصماً مزدوجاً أبداً.
- **إطلاق الويب والموبايل بقاعدة كود رشيقة:** تسليم تطبيق فعلي على Google Play بالتوازي مع منصة الويب.

## 05 · أهم القرارات الهندسية والمقايضات

| القرار | البدائل المدروسة | لماذا كان هذا الخيار الأصح |
|---|---|---|
| **فصل الطلب الرئيسي (`orders`) عن الطلبات الفرعية (`sub_orders`)** | جدول منتجات مسطح يكتفي بعمود `vendor_id` | عند إلغاء تاجر لمنتجه مع استمرار شحن تاجر آخر، الجدول المسطح يعقّد الاسترجاع الجزئي وحساب الشحن. الفصل يجعل لكل تاجر دورة شحن وتسوية مستقلة تماماً. |
| **طبقة تجريد للبوابات (`PaymentGatewayContract`)** | كتابة كود كل بوابة داخل الـ Controller | اختلاف طرق التوقيع والعملات والـ callbacks بين Stripe وPayPal وميسّر كان سيفسد منطق الدفع. طبقة التجريد أبقت مسار الشراء موحداً وقابلاً للاختبار. |
| **دفتر قيود إضافي فقط (`ledger_entries`) للعمولات** | تعديل رقم `balance` مباشرة في جدول التاجر | تعديل الرصيد مباشرة يضيع أثر التدقيق عند أي نزاع مالي. تسجيل القيود (دائن، عمولة، سحب) يضمن مطابقة مالية دقيقة لكل قرش. |

## 06 · حماية الـ Webhooks ضد التكرار (Idempotency)

```php
declare(strict_types=1);

final class ProcessPaymentWebhookAction
{
    public function handle(string $gateway, string $eventId, string $orderRef, int $paidMinor): void
    {
        DB::transaction(function () use ($gateway, $eventId, $orderRef, $paidMinor): void {
            $alreadyProcessed = WebhookEvent::query()
                ->where('gateway', $gateway)
                ->where('external_event_id', $eventId)
                ->lockForUpdate()
                ->exists();

            if ($alreadyProcessed) {
                return;
            }

            WebhookEvent::create([
                'gateway' => $gateway,
                'external_event_id' => $eventId,
                'processed_at' => now(),
            ]);

            $order = Order::where('reference', $orderRef)->lockForUpdate()->firstOrFail();

            if ($order->status === OrderStatus::Paid || $order->total_minor !== $paidMinor) {
                throw new PaymentMismatchException("Order {$orderRef} failed integrity check.");
            }

            $order->markPaid();
            SettleVendorCommissionsJob::dispatch($order->id)->afterCommit();
        });
    }
}
```

## 08 · ما الذي سأطوره بشكل مختلف لاحقاً

> في البداية كان يتم جلب أسعار صرف العملات عند لحظة إتمام الطلب، ما قد يضيف تأخيراً طفيفاً عند بطء الشبكة. نقل أسعار الصرف إلى Snapshot مجدول في Redis يتحدث كل 15 دقيقة ويُثبّت داخل سجل الطلب لحظة إنشائه يفصل تماماً مسار الدفع الحرج عن أي اعتماد شبكي خارجي.
